# Startup: the timeline, the launch, the cold path and the boot placeholder

## Timeline

Every start logs its milestones to clack.log (`internal/applog/startup.go`), in ms since the OS started the process (`applog.ProcessStart`: the kernel's start time on macOS, /proc on Linux, GetProcessTimes on Windows), so the loader, the Go runtime and every package's init count too (before 2026-11-21 the zero was main). `debug:` lines are on for the first 60 s, and always with `CLACK_DEBUG=1`:

```
debug: startup +3ms window
debug: startup +118ms first-frame (background, fonts loading)
...
debug: startup +172ms js-runtime (in 154ms, err=<nil>)
...
debug: startup +668ms data-ready
debug: startup +937ms reveal (cap, was waiting for plugin renders; 70 plugin deliveries from 68 roots (most: root 1, 3))
startup: timeline settled=937ms window=1ms first-text=83ms js-runtime=172ms … data-ready=668ms reveal=937ms relayouts=0
```

| milestone | when |
|---|---|
| `main` | main started: the loader, the runtime and the package inits are done |
| `single-instance`, `creds`, `ui-new`, `attached`, `app-main` | main's steps: no other Clack runs, the credentials read, ui.New, the session attached, the main thread enters the OS's loop (macOS: AppKit) |
| `run`, `window`, `event-loop` | App.Run started; the window's Go side exists; its event loop starts |
| `appkit-app`, `appkit-run`, `will-finish-launching`, `launched`, `activated` | macOS (Gio patch 56): NSApplication made, its run loop starts, applicationWillFinishLaunching, NSApplication finished launching (the Dock's bounce ends), applicationDidFinishLaunching made the app active (the main window opens right then) |
| `gio-init`, `window-create`, `window-view`, `window-ns`, `window-shown` | the window: Gio's Window.init; macOS: the main thread starts making it, its view (the Metal layer), its NSWindow; the OS window on screen (makeKeyAndOrderFront, ShowWindow, XMapWindow) |
| `config`, `frame-event` | the window's first ConfigEvent and FrameEvent |
| `gpu-context`, `gpu`, `presented` | the first GPU context, the first gpu.New, the first Present |
| `fonts` | the text shaper is built (the UI font, the system font index) |
| `first-frame` | the first frame was submitted (background only while fonts load) |
| `real-frame` | the first frame of the client itself, not the boot placeholder: what a launch is for |
| `menu-bar` | macOS: the menu bar installed on the main thread (after the first frame) |
| `first-text` | the first frame with text |
| `theme` | the first frame with the account's own theme (`account`) or Slack's default when the account has none |
| `sidebar` | the first frame showing sidebar rows |
| `messages` | the first frame showing the open channel's messages |
| `cache-read` | the warm boot's disk reads resolved: `warm: N convs…` or `cold: <why>` |
| `sidebar-cached` | a warm start's sidebar from the boot data is applied (before Slack answered) |
| `core-ready` | core.Boot finished (conversations, counts, sections, prefs… answered) |
| `sidebar-live` | Slack's answers are in the sidebar |
| `js-runtime`, `taut-started`, `slick-started` | the plugins' JS engine is up; the plugins enabled at start have started |
| `data-ready` | boot data and the open channel's header are in |
| `images` | no image fetch or decode left after messages and sidebar were shown |
| `plugins` | the plugin runtimes attached (`none` without plugins) |
| `reveal` | Slack's boot placeholder gave way to the client (see below) |
| `settled` | the last change before 1.5 s with nothing new (or `[timeout]` at 60 s) |

`relayouts` counts frames where something already painted moved, by kind: `sidebar` (rows added, removed, reordered or relabelled), `unreads` (a row's unread or mention state), `messages` (a visible message row moved or resized), `theme` (the account theme changed after the first frame, the default-theme flash of a cold start).

`.github/perf/launch.py` launches the real app as a user does (macOS: Clack.app through LaunchServices) and tabulates these per run, cold, warm and with the OS file cache purged (flake-check's `launch-speed-mac`, `-linux`, `-windows`; see the launch, below). The perf workflow (`.github/perf/startup.sh`) runs cold and warm starts of the base and HEAD against a Hack Club-sized fakeslackd answering every API call after 150 ms and every image after 40 ms, with a non-default account theme. `cold` starts have nothing on disk (no metadata cache, no boot data, no compiled JS engine, no saved theme or plugin slots), `warm` starts what a normal start has; every frame's layout and total time is logged too (`CLACK_FRAMELOG`). The table is on the run page ("Startup timeline"). `CLACK_NO_WARM_BOOT=1` starts cold even with boot data on disk (and reads no header cache).

## The launch

Karim (2026-11-21): "Make launching the app take less than a Mac app bounce." macOS bounces an app's Dock icon from the launch until the app finishes launching; one bounce on CI's runner is 700 ms (`.github/perf/bounce.sh` films an app that takes 6 s to finish launching and times the icon: 8 bounces, each 683-717 ms). So the window must show the client from the cache within that, and Clack's own work must never hold AppKit's main thread before the window.

What a macOS launch does, in order: the loader and the runtime (`main`, ~35 ms warm on CI), main's setup (~2 ms), then the main thread enters AppKit (`app-main`): NSApplication (~45 ms), its launch (`launched`, ~120 ms after `app-main`, LaunchServices' part included), the window (`window-create` to `window-shown`, ~35 ms, most of it AppKit's NSWindow), the first frame (layout ~18 ms, the GPU ~55 ms on the runner's virtual GPU). Meanwhile, off the main thread:

- App.Run starts the backend (the boot data, header cache and meta.json reads, core.Boot's calls) at once, before the window's place is known: on macOS the displays are AppKit's, which answers only once NSApplication runs, so reading them first (as before) held every disk read until after the launch. The displays are asked for at the top of Run and come from `applicationWillFinishLaunching` (Gio patch 56 reads the screens there; the main thread serves its queue only after the launch), and the window opens inside applicationDidFinishLaunching, the moment NSApplication finished launching and the app is active (before, its main-thread block waited for AppKit's post-launch work, 30-50 ms on CI).
- The fonts load from ui.New on (`fonts`), the warm data in `cache-read`; both land well before the first frame on a warm launch.
- meta.json loads in two parts (`store.LoadCacheBase`, layout 2: the small keys first): what the first frame reads (the users, prefs, channel names, bots, experiments), which the warm snapshot waits for, then the custom emoji and the user groups (6.6 MB of packed emoji and 0.4 MB of groups on Hack Club), after the window's first real frame (`DeferCacheRest`, `FirstFrameDone`; 1.5 s at most), as Slack loads custom emoji after its first render. The few custom emoji the first frame draws (the sections' icons, the sidebar DMs' and the viewer's status emoji, the cached tab bars' bookmark and title emoji) come with the boot data (`BootData.Emoji`), so it draws them as before; a meta.json from before the layout loads whole, once, until the next save rewrites it. Until the second part is in, nothing saves meta.json. The user groups load 5 s after boot and save meta.json when they changed, as emoji.list's answer does: the Dock's Quit ends Clack without the save on quitting (nothing answers `applicationShouldTerminate:`; only the menu's Quit saves), so they would otherwise wait for the 5 minute save. Measured on one runner, A/B alternating (flake-check, launch-speed's temporary `launch-cache-ab`; warm medians in ms since exec): with Hack Club's cache (meta.json 7.17 MB: 77,770 emoji, 6.4 MB packed, 2,003 groups) on a fast runner (run 44963050899), cache-read went from 142 to 68 and the warm load from 86 to 26 ms. The first frame stayed at 266-274: there the window, not the cache, is the critical path. With the same emoji and no groups on a runner 2.1x slower (run 44959171159), cache-read went from 431 to 162, the warm load from 287 to 50, data-ready from 539 to 475 and the first frame from 634 to 559. The decode on another core also slowed AppKit's own launch (`launched` 386 against 322). The second part decodes in 70-400 ms, after the first frame.
- The menu bar installs after the first frame (`firstFrameDone`): its install took the main thread 9-13 ms warm, 35-80 ms with a cold file cache, between `launched` and the window. Until then Gio's stub menu (patch 56) has Hide, Quit (through Clack's own Quit: `app.SetQuitHandler`), and the window's Minimize and Close.
- The plugin runtimes are made at once (`startTautAsync`): taut.New and slick.New read the plugins, the Slick theme and the user CSS and install the sheets (Go only, a few ms), and the reveal waits for them, so the client's first frame is in its theme (a frame before them would be repainted whole). Their plugins (the JS engine) start at once too, unless last session's plugins showed nothing of their own (no patched component, no CSS: ui.json's `plugin_patched` and `plugin_styled`): then after the first real frame, so they don't take the CPU it needs.

CI's numbers (macOS 26 runner, an M1 VM with 3 cores; fakeslackd at 150 ms per call; ChatTabs and five Taut plugins; ms since exec, warm medians): before (cd583d6c with the marks) the window was on screen at 197, its first frame at 269 and the client at 407, after the boot placeholder had waited out the plugins' 100 ms cap on every warm launch; after, the client is the first frame, at 292. The runners' speed varies about 2x from run to run (two VMs a host): on slow ones the same pair measured 868 (746-985) against 580-633. `launched` to the window went from 15-70 ms (a main-queue round trip, the menu bar's install) to 0-1. Linux (Xvfb, llvmpipe) went from 606 to 271 and Windows from 567 to 307 (both had waited for the same cap). LaunchServices adds 25-120 ms from the launch call to the process start on a warm launch, 1-4 s on the first launch of a new build. A purged launch (warm, the OS file cache emptied) is 1.5-2.9 s, nearly all AppKit paging itself in.

The launch budget (ci.yml's macos job, flake-check's `launch-budget`; `.github/perf/launch-budget.sh`): Clack.app launched through LaunchServices, with a Slick theme, Taut's and Slick's user CSS and plugins that show nothing of their own, once cold and seven times warm. Every launch's first real frame must be in the theme (`real-frame`'s detail logs the window's, the sidebar's and the pane's colours; a sheet recolouring the client after it showed counts as a `palette` relayout), the median warm launch may show the boot placeholder at most one frame (16 ms) before the client (cd583d6c: 97-147 ms on every warm launch), and the fastest warm launch should show the client within one bounce (700 ms) of the launch call, at the speed of the fastest runner seen: a failure in flake-check's job, a warning in ci's. The runners' speed varies 3-4x from run to run, and a launch slows all over, macOS's own part as much as Clack's: on the fastest runner seen (ci on 9d20140f) LaunchServices' exec plus AppKit's finishLaunching (`will-finish-launching` to `launched`) took 71 ms on the fastest warm launch and the client showed 225 ms after the launch call; on slow runners they took 202-232 ms and the client showed at 723-787 ms. So the budget is one bounce times this runner's part over 71 ms (never less than one bounce). That gives 254 and 241 ms at the fast runner's speed for those two runs (`launch.py`'s `runner_speed`).

## The cold path

Everything a start needs goes out at once (core.Boot and backend.start):

- **Boot batch:** users.conversations (then, straight away, users.info for the DM rows' people), client.counts, users.channelSections.list (truncated sections page in parallel), experiments, sidebar.dms, users.prefs, team.prefs, team.info, stars.list, saved, self + the rail icon, emoji.list. meta.json (users, emoji, groups) decodes alongside instead of before them. emoji.list (~7 MB, 65k entries on Hack Club) is scanned straight into the store's packed form (`slack.PackEmojiJSON`; encoding/json took ~300 ms) and written to disk off the critical path. Up to 16 calls are in flight (`slack.MaxConcurrent`).
- **The restored channel** (ui.json's route): its history and header (conversations.info tabs, bookmarks, member count and facepile: three reads at once in `backend.opened`), and the drafts' sidebar markers, start at t=0, not after boot.
- **Plugins:** the JS runtime, the bundles (QuickJS bytecode from the cache) and the enabled plugins start at t=0 too. Taut's `StartEnabled` no longer waits for core; the redux mirror reads `core.SnapshotNow` (never blocking the JS thread) and re-reads everything at the `booted` event.
- `{"ok":true` bodies skip the extra full parse that only read `ok`.

## Boot placeholder

Slack's page holds `div.p-client_container_placeholder` (a theme background, a sidebar block and a content panel) under `div.p-client_container`. client-boot's "Render Placeholder" hook (`renderBootPlaceholder`) colours it from what the last session stored for the team at renderComplete ("Save channel sidebar and team switcher colors"): the stored iaTheming's window gradient (the flat primary without window gradients), the sidebar block `rgba(255,255,255,.9)` (`.11` for an inverted light sidebar, `rgba(16,18,20,.6)` dark) as wide as the last sidebar, the content panel `#fff` (`rgb(26,29,33)` dark). With nothing stored it is page.html's `#bbbabb` (`#282828` dark). React mounts the client over it in renderApp ("Render React"), after bootDataFinished ("Finish waiting for boot data"), or from the persisted store on a warm boot; the channel then shows its own loading state until its history arrives.

Clack draws exactly that placeholder (`internal/ui/reveal.go`, from the first frame, before fonts are loaded) and keeps the account theme in ui.json (`acct_theme`) the way Slack keeps its colours per device. It renders the client once the sidebar's data is in (the boot data on a warm start, below; else core booted), the restored channel's header is in (Slack's boot data carries it in the channel object; on a warm start the header cache has it), the plugin runtimes' sheets are in (the user CSS and the Slick theme, which taut.New and slick.New install in Go), and the plugins enabled at start registered and delivered their first renders (Taut's patches render synchronously with Slack's React; Clack's plugins render on their own thread, so it waits for their deliveries to go quiet, at most 100 ms after the data). A warm start waits for those renders only when they would change what it shows: when its frame drew a component last session's plugins patched (ui.json's `plugin_patched`, watched for by slackc's `SetExpected`) outside a slot reserved for its tree, or those plugins added CSS of their own (`plugin_styled`). Otherwise the slots their trees took last session stay reserved (below) and the window shows the client from its first frame. Messages and images don't hold it. Re-layouts are counted only after it.

## Warm boot

Slack's client keeps its redux store in IndexedDB per team and user and, when one is there, renders from it before any boot call answers (client-boot, build 2c0d02ca130f): `getContextualInfoForTeamId` sets `isBootingWarm` from `maybeGetStoredState` → `getStoredStateIfValid` (IndexedDB keyed by team and user; skipped when the team expired, the store is older than the minimum data version, or holds no bootData), and in `runBootTeam` `renderApp` then waits only for the store hydrated from it (`dataSetupStore`, `setInitialState`), the translations and the render module: `getBlockingStatus(e,t){return t?"nonblocking":e}` makes every registered boot API nonblocking on a warm boot, and each one's answer is dispatched into the store when it comes. Its persisted stores include channels (tabs ride in `properties.tabs`), channelSections, unreadCounts, prefs, members, membershipCounts, files, messages and channelHistory; bookmarksStore is not persisted. In the channel the messages show from the persisted store, or `c-channel_loading_state` until the history arrives.

Clack does the same with the part the first frame shows (`internal/core/warmboot.go`, `internal/store/bootdata.go`):

- Boot reads `boot_data.json` (the team, the sidebar's conversations, sections, unread counts, open DMs, starred, the Activity badges) and `headers.json` while `meta.json` decodes. Once all three are in, the boot data is installed where Boot hasn't answered yet, a snapshot is built from it, `DataReady` closes and core emits `hydrated` (the plugins' state mirror re-reads, as at `booted`).
- The UI applies that snapshot (`core.WarmSnapshot`) and the restored channel's header from the header cache, and the placeholder lifts on them; a restored channel the header cache doesn't have doesn't hold it (Slack renders whatever its persisted store has), and its tabs come with their read.
- Each of Boot's sidebar answers is installed when it arrives (Slack dispatches every boot API's answer into its store on arrival) and announced, so the UI follows it: conversations (cached ones Slack no longer lists leave), counts, sections, sidebar.dms, stars. A call that fails keeps the cached part, and data that didn't change changes nothing on screen.
- The window is usable meanwhile, so an answer can land after a write it doesn't know about. Every change to the sidebar's state moves a journal (`internal/store/journal.go`): a mark or a new message per conversation, a leave, archive, join, open, rename or close per conversation, a DM's open flag, the section list, the Activity badges. An answer keeps whatever changed after its call went out (Boot's, and `refreshCounts`', `FetchSidebarDMs`', `refreshSections`' too). Counts merge per field: a mark made meanwhile keeps its cursor; a message alone takes Slack's cursor and mention count (it knows mentions below a partial mark the client can't count) and stays unread when it is newer than the answer. An answer that merged anything is partly older than Slack is: Boot reads the counts or the sections once more after it finishes, and `refreshCounts` reads once more (not again after that).
- Every channel opened shows its last header at once (tab bar, folder bookmarks, facepile, member count) while its reads revalidate it; a read that brings the same header draws nothing, and a failed read keeps the bar.
- Both files name their account and are read only for it (`ReadBootData`'s team and user check, besides the per-account directory). They are written 20 s after boot, every 5 minutes, and as the window closes (before plugins' stop hooks), only after a Boot that answered. Sign-out deletes them first, at once, and leaves a signed-out mark (`store.SignOutNow`; meta.json and the images follow in the background); a session that ended (auth_failed) deletes them, and no save already under way writes them again; a start finishes a sign-out whose process ended first (`store.SweepAccounts`, the marked directories; never the signed-in account's, whose stale mark it clears, as signing in again does). Other signed-in accounts' (the account switcher's) keep theirs, as Slack keeps a persisted store per signed-in team.
- Not copied: Slack boots cold again once its last cold boot is a week old (`hasBeenTooLongSinceLastColdBoot`), since its warm boot fetches conversations incrementally (`minChannelUpdated`) and can drift; Clack's refetches every list whole. Slack also persists messages; Clack never writes message content, so the restored channel shows its loading state until the history arrives.

The UI goroutine never waits for Boot: core's `Snapshot` (and `BootErr`) wait, so UI code reads the backend's model, `RecentSnapshot` or `SnapshotNow`, which don't. A wait longer than 50 ms is logged (`core: Snapshot waited Nms for boot (<caller>)`), a wait on the UI goroutine is a uiguard violation, and `TestNoBootWaitOnUIPaths` (a source scan), `TestUINeverWaitsForBoot`, `TestActivityNeverWaitsForBoot` and `TestStartupStatesNeverBlock` fail on one.

## What stays on disk

`<cache root>/v1/<team>-<user>/` (`internal/store/cachedir.go`); the cache root is the OS's user cache folder (`~/Library/Caches/Clack`, `~/.cache/clack`, `%LocalAppData%\Clack`), `<CLACK_HOME>/cache` when `CLACK_HOME` is set, or `CLACK_CACHE_DIR`. Directories are 0700, files 0600, written through temp files renamed into place. Nothing in it is message content.

| file | holds |
|---|---|
| meta.json | the user directory (always including the sidebar's DM people), all custom emoji, usergroups, prefs, channel names, bots (saved off boot's critical path) |
| boot_data.json | the sidebar a warm boot renders first (team, conversations without their latest message, sections, unread counts, open DMs, starred, Activity badges) |
| headers.json | the 100 most recently opened channels' tab bars (with the folder tabs' bookmarks), facepile ids and member counts |
| img/ | avatars and emoji; 384 MB, least recently used out |

Elsewhere: ui.json (per device) keeps the account theme for the boot placeholder (`acct_theme`) and the plugin slots (`plugin_slots`); `taut/cache` keeps the JS engine's compiled code and the bundles' bytecode. Sign-out deletes the account directory, and nothing is written after it. Older `vN` directories are deleted at start, and so is what alpha.28's boot snapshot left (`boot.json`, `history.json`).

## alpha.28's boot snapshot, and why the warm boot came back

alpha.28 painted warm starts from a persisted snapshot (sidebar, counts, the last channel's 50 messages), like Slack's IndexedDB store. On the perf workflow (150 ms per API call, ChatTabs and five Taut plugins) it lost: the same binary revealed at 932–937 ms without it and 981–988 ms with it (run 42765182591), because there the plugins, not the data, set the time, and the snapshot added its own read and reconcile. It was removed with its disk writes, and with it the last message text Clack wrote to disk.

The real network isn't 150 ms per call. Karim's clack.log (2026-11-15, Hack Club, 1,655 conversations) has users.conversations at 1.26–2.41 s and users.prefs at 1.0–1.5 s, the restored channel's header reads at 0.7–1.3 s, and the placeholder lifting at 2.1–2.9 s although the first frame was at ~0.7 s and the metadata cache loaded in 96–180 ms. The warm boot above takes the network off that path again, without any message on disk: the reveal waits for the disk reads, the first frame and at most 100 ms of plugin renders, about 0.8–0.9 s on that machine.

## Plugins at start

The JS engine starts at t=0, except on the real window's launch when last session's plugins showed nothing of their own (no patch, no CSS): then after its first real frame (the launch, above). With its compile cache (`taut/cache`) it is up in ~170 ms on a CI runner; without one (the first start ever, or after a wazero or engine change) wazero compiles the 1 MB engine for ~1.3 s. Plugins start 30–150 ms after the engine. Their first renders mount component by component (ChatTabs, WhoReacted, LastSeen… ~70 roots for 50 messages), one layout per step: under the placeholder each step is a layout only, the placeholder alone goes to the GPU.

The placeholder waits for plugins at most 100 ms after the data is ready (a warm start only for chrome its first frame shows, above). A plugin that renders later doesn't move anything when it wraps a component it wrapped last session: the insets of the original inside the plugin's tree are kept in ui.json (`plugin_slots`), and until the plugin's first tree arrives the native component draws inside them (`internal/ui/slackc/reserve.go`). Slots are released once the plugins started and their renders were quiet for a second (10 s at most), and the learned ones are saved.
