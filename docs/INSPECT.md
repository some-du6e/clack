# The inspect tool

Clack's inspect tool is a developer shortcut for UI bug reports. It is not a Slack feature, so nothing about it shows until it runs: no menu item, no Preferences row, no button.

## Turning it on

Type the Konami code anywhere in the main window: ↑ ↑ ↓ ↓ ← → ← → B A. The tool is on at once, with no relaunch, and a toast says so. Clack keeps it on (`"inspect_tool": true` in `ui.json`). The code again turns it off.

The keys still do what they always do wherever you type them: the arrows move the caret, B and A type, and in an empty composer ↑ opens your last message for editing (Esc leaves it as it was). Clack only watches them go by (Gio patch 28, `third_party/gioui.org/CLACK_PATCHES.md`).

Two other ways, both read at launch only:

- the environment variable `CLACK_INSPECT=1`. A Clack opened from the Dock or Finder doesn't get a shell's variables, and a second launch hands over to the running Clack, so on macOS quit Clack (⌘Q; closing the window only hides it) and start `/Applications/Clack.app/Contents/MacOS/clack` from a shell that has it.
- `"inspect_tool": true` in `ui.json` in Clack's config folder: `~/Library/Application Support/clack` on macOS, `~/.config/clack` on Linux, `%AppData%\clack` on Windows. Edit it with Clack quit: Clack writes `ui.json` from what it read at launch whenever a setting changes, the window moves or you switch conversations, so an edit made while it runs is lost.

Then Hyper+D starts a session: ⌃⌥⇧⌘D on macOS, Ctrl+Alt+Shift+D on Linux and Windows (where Super may be held too). The shortcut works over modals too, so dialogs can be inspected.

The tool works in each of Clack's other windows too: the huddle window, a screen share popped out of it, the presenter's panel while you share, a huddle's invite window and the join preview (Karim, 2026-11-20, on Windows in a huddle: "no dev tools" / "they dont appear"; it ran only in the main window). Each of them runs its own event loop and theme, so each runs a tool of its own, on while the main window's is (turning the tool off in the main window takes it from them at their next frame). Hyper+D in the window starts its session, and the picks, dragged regions, review, blur and freeze are the main window's (huddleui/inspect.go). A report names the window as its page and its outermost region (`huddle window`, `screen share popout`, `presenter panel`, `huddle invite`, `huddle preview`), with the huddle window's title bar and toolbar and every popup over it as regions inside. The huddle window's menus, pickers and modals are layers of the record, as the main window's are, and the tool's toasts are drawn in the window. A window records its frames under slackc's frame lock, which the main window and the huddle window already took for their patch points: the record is slackc's, one window's frame at a time. An experiment is noted only from the goroutine recording the frame, so one read by another window meanwhile goes to no node (`TestExperimentNotesFromTheRecorder`). Sessions in two windows at once each get the shots' GPU window: it stays while any session wants it (`TestShooterTwoSessions`). The animated images stay held while any window is frozen (`App.InspectHold` counts the freezes). `TestInspectHuddleWindow`, `TestInspectScreensharePopout`, `TestInspectPresenterPanel`, `TestInspectInviteWindow` and `TestInspectJoinPreview` run the shortcut, the freeze, a dragged region's review and copy, the toast and the tool turned off in each window, frame by frame as its run loop draws it, against the fake meeting and fakeslack. The presenter's panel opens without the keyboard focus (Gio patch 8: Slack's showInactive), so click it before Hyper+D.

Until Gio patch 29 the shortcut, then ⌥⇧⌘D, did nothing on macOS. AppKit sends no command for a ⌘ press with ⌥ held (`interpretKeyEvents:` calls neither `doCommandBySelector:` nor `insertText:`), and Gio dropped every ⌘ press that came without one, so no key filter ever saw it; Hyper+D has ⌥ too. `TestMacInspectKeys` on ci's macos job posts the keys through AppKit as a keyboard makes them.

## A session

A banner at the top says the session is on: "Inspect: click or drag to blur, then copy · shift-click copies at once · ↑ ↓ parent · F freezes · Esc to stop". The Slack component under the pointer gets a pink outline and a label with its name, root element and size; one of the chrome's elements (below) gets one with its selector. ↑ widens the outline to the enclosing element or component and ↓ comes back. F freezes the window on the frame on screen (below). Esc or Hyper+D again ends the session, though in a frozen window the first Esc only unfreezes it.

The window keeps working while the session runs, minus clicks and keys. Hover states still show (a message's toolbar, tooltips), lists scroll, and carets, focus rings and animations stay as they are. No button, editor or shortcut reacts. The tool alone reads the clicks and keys. Gio patch 21 (`Source.HoverOnly`, `third_party/gioui.org/CLACK_PATCHES.md`) makes that possible. The window also drops its system action areas for the session (the top nav's drag area on macOS, Linux and Windows, the Windows caption buttons): the system acts on a press there before Clack sees it, so it would move the window instead of picking or dragging.

There are three ways to capture:

- **Click** an element: the outlined element is captured and the review below opens first, so parts of it can be blurred out before anything is copied. A press that moves less than 6 dp before it comes up is still a click.
- **Shift+click** an element: the same capture, copied and saved at once with no review, and the session ends. Shift counts if it is held at the press or at the release. (Until 2026-11-17 these two were the other way round; Karim asked for the review on every plain pick.)
- **Drag** a rectangle, for what the picker can't outline: once the pointer has moved 6 dp pressed, the window dims around the rectangle being dragged out and its size shows beside it. Releasing captures that region as it is and opens the review. Esc with the button down drops only the press or the drag, and the session goes on. A region thinner than 8 dp grabs nothing.

Every way, Clack renders the capture from the release's frame, or in a frozen window from the frozen frame, again through a headless GPU context (the window's own GPU can't read frames back). It draws the crop at 4 px per dp whatever the display, under a transform over the frame's ops (Gio patch 31, `Ops.Whole`). Paths and glyphs are vectors, so the element comes out as sharp as a window four times as dense, and the image stays small enough that Slack shows it near its own size. A crop whose image would pass 3200 px is drawn less dense, never below the window's own px. For a click or a Shift+click the crop is the element and 24 dp around it. That margin gets blurred past reading (a 5 dp box blur, three passes) so the neighbouring messages, channels and names are smears, and the element is outlined. For a drag the crop is the region itself, with no margin, no blur and no outline.

The review is drawn in the frame after the pick's, whatever the size of the shot (Karim, 2026-11-18, on Windows at 1918x1080: "this shit takes to long between a selection and the blur page"; the banner said "Blur: preparing the shot…" for seconds). Two things held it. First, the margin's blur ran over the whole shot in a goroutine, and the review waited for it: 0.5 to 0.8 s for a 3200x2000 px shot on CI's runners, and the copy did it once more after Enter. The blur now runs only where the margin needs it, with the same integer arithmetic, so every pixel is the old one bit for bit (`TestBlurMatchesOld`, `TestPaintShotMatchesOld`), split over the CPUs, in milliseconds. It's done when the shot is taken, so the next frame has it. Second, every shot made a headless GPU context, a device and a GPU when it was taken: up to 1.2 s for the first in a process on Mesa's llvmpipe. A session now makes its headless window as it starts, off the UI goroutine, so the pick finds it ready ("gpu ready" in the stage-time line), and the shot gives its framebuffer the shot's size (Gio patch 52, `Window.SetSize`). A session takes one shot, so the window is let go of as soon as the shot is read back rather than kept through the review (the framebuffer alone is 31 MB for a whole-window shot), and nothing on the UI goroutine waits for a window being made or let go of. What the review doesn't need to appear waits until it's needed: the rectangles' blurs until they're drawn, and the colours, the composed image, the PNG, the file and the clipboard until Enter, all off the UI goroutine.

The shot itself still runs on the UI goroutine, since the frame's ops are good only for that frame, and the window waits for it. On a GPU that's milliseconds. On a software one it's not: for a shot of most of a 1918x1080 window, CI's runners take 1.1 to 1.7 s at 1x and 2.6 s at 2x, mostly WARP's readback on Windows and llvmpipe's render on Linux. So the review comes in the first frame after the pick, but that frame comes that much later there, the window is frozen meanwhile, and at 2x the freeze watchdog's 2 s can pass. A pill-sized shot takes 50 to 110 ms on the same runners.

Enter or Mod+C pressed in an element pick's own frame copies the image the review's Enter would (nothing marked) with no review: the element's margin is blurred anyway. A dragged region opens its review all the same, since the review is the only place a region can be blurred, and so does a pick that found no component and no element (a shell column, or a layer with nothing recorded in it, such as the lightbox's whole window), which can be as big as a region. Their copy keys work only once the review has been on screen for 300 ms: from the first frame whose input is read after a frame drew the review (so that frame was submitted). Until then an Enter, Return or Mod+C is dropped, the banner leaves "Enter copy" out, and the tool asks for a frame at the moment it adds it. A dropped key is held as well: its auto-repeat presses (Windows and macOS repeat a held key as presses with no release between them) are ignored until it's released, with Enter and Return as one key. A pointer Cancel (the window losing the focus) or the session's end lets it go, and so does a press 2.5 s or more after its last, since the slowest repeat settings wait about 1.8 s and such a press came after a release that went to another window. So a region never goes out unseen, whether the Enter came with the release, while a software GPU took seconds over the shot, or as the review's first frame was still being drawn (`TestRegionCopyArms`, `TestHeldCopyKeyRepeats`, `TestInspectRegionArming`). An element pick's Enter in the frame after its pick copies, and its stage-time line says "before the review showed"; a capture with no shot goes as text at once, and its line says "no shot: copied as text at once". Esc in the frame a press is let go of drops only that press, as Esc while pressing or dragging always has: nothing is shot and the session goes on. Captures are saved and copied in the order they were taken, so the clipboard ends with the newest even when an older, bigger one takes longer to compose (a report that falls back to text is handed to the window's clipboard by the tool, and the next delivery waits for a frame after that), and reports of the same second are saved as `inspect-YYYYMMDD-HHMMSS_2`, `_3` and so on, which sort after the second's first. Every capture logs one line of its stage times to Clack's log, whatever ends it (a copy, Esc, the tool closed) (`inspect: capture click, window 1918x1080 px at 1x, shot 3200x2383 px at 2.24x: report …, shoot … (gpu …, render …, readback …), review shot ready …, review drawn … after the pick (N frames); Enter … after the review showed: colours …, compose …, png …, save …, clipboard …; copied as an image`). `TestInspectReviewTiming` runs it at 1918x1080, at 1x and 2x, on WARP (windows-applog) and llvmpipe (linux-idle).

### Popups

Modals (Block Kit's and Clack's own), menus and their submenus, popovers (the rail's peeks, the Focus peek, the search card's preview, kit's calendar and select), the emoji picker, profile cards and the app card, the Ctrl+K switcher, Block Kit's select dropdowns, date and time pickers (Block Kit's, Schedule message's, search's, Preferences'), select and option lists, the shortcuts picker, channel details, search's filter selects, the colour picker, the composer's conversation picker and coachmark, the lightbox, the apps browser, toasts (`toast`: `layoutToast`, Slack's toasts and the rich ones record themselves as a layer boxed at the toast), plugins' overlay roots (Taut's and Slick's modals and menus, a `<dialog>` shown modal), tooltips in either theme (a plugin tree's title tooltip too), and the ones the thread pane opens are layers of the tool's record (Karim, 2026-11-18: "you cant select the popup smh"; his capture over an app's Block Kit modal said `region primary`). The picker outlines the element under the pointer in the topmost layer, never the window under it, and a click or a Shift+click reports that element: its component, element and classes, with the popup as its region (`modal (blockkit.Stack)`, `menu (popups.Menu)`, `submenu (popups.Menu)`, `menu (blockkit.selectMenu)`, `popover (popups.Popover)`, `popover (popups.SearchPopover)`, `emoji picker (popups.EmojiPicker)`, `profile card (popups.ProfileCard)`, `plugin overlay`, `plugin dialog`, `tooltip`). An overlay can name itself, and a wrapper is named by what it wraps: Block Kit's date picker is `date picker (popups.dtCalendar)`, its time picker `time picker (popups.dtTimeList)`, a basic select's list `select list (popups.dtTimeList)`, the shortcuts picker `shortcuts picker (blockkit.picker)`, search's filter select `filter select (popups.srFacetSelect)`. A dialog stacked on channel details (Leave, Archive, Add people, Edit topic) is picked as its own SK modal card (`c-sk-modal`, 520 dp), not as the details card under it. What's around the popup's layer, the window under it, isn't in its report. A dragged region over a popup names the popup among its regions. The freeze holds popups as it holds the rest, so a tooltip or a hover card that would go when the pointer leaves its trigger stays to be picked.

How: ui's `drawOverlay` records each overlay as a layer (`slackc.InspectOverlay`), slackc's `LayoutOverlays` each plugin overlay root, and the tooltips every tooltip drawer shapes (`theme.TooltipShape`, and a plugin tree's in a light theme, which draws no outline) record themselves as one. A popup's boundaries lay out over the whole window, as its scrim does, so its card gives them and the layer their box (`slackc.InspectCard`). The picker keeps the node recorded last, so a popup that lays its content out before it draws its card around it (ProfileCard, every `popups.Popover`) records the card first, as an inspect mark it ends at the card (`InspectMark.EndCardAt`): its content is inside the card and wins over it, and the card is what's picked where nothing in it is. An element entered after everything it holds was recorded gets no area from `InspectCard`, or it would be picked over all of it. An overlay that gives its layer no box is boxed by its own `Rect` when the layer ends, so a pick on its card where nothing was recorded is still the popup's. `TestOverlayKindsBoxTheirLayer` reads internal/ui's sources and fails for an overlay kind (Layout and Dismissed, not invisible) that does neither and doesn't lay out a popup that does; the one with no card (the profile preview's dim around the pane) is listed with why. In a session, a layer that ends with no box anyway logs `inspect: overlay <name> drew no card box` once per layer name (`shortcuts picker (blockkit.picker)`: a wrapper by what it wraps); the profile preview's dim says it has no card (`InspectNoCard`, which the test requires of what it lists, and of nothing else) and logs nothing. The elements a popup enters for CSS (a menu's rows, a modal's buttons) get boxes inside layers only (`slackc.InspectAreaInLayer`), so picks in the window stay as they were. The parts Clack draws without entering a class are recorded by Slack's names (`ClassDef.Inspect`, which nothing styles see): the SK modal's `c-sk-modal_header`, `c-sk-modal_title_bar`, `c-sk-modal__close_button`, `c-sk-modal_content` and `c-sk-modal_footer`; a Block Kit modal as Slack's `BlockKitModal` draws it (a `WizardModal` over `DeprecatedBaseDialog`: `c-dialog__header`, the `h1.c-dialog__title` with `p-block_kit_modal__title`, `c-dialog__close`, `c-dialog__body`, `c-dialog__footer` with `c-wizard_modal__footer`'s back and next buttons, each block in its `p-block_kit_renderer__block_wrapper`); the emoji picker's `EmojiPickerInput`, `EmojiList`, `EmojiListRow`, `EmojiListGroupItem`, each emoji's `EmojiListEmojiButton` (`p-emoji_picker__list_item`, `--a11y-not-selected` on all but the selected one, `key_selection` on the keyboard's, `data-qa=emoji_list_item`) and the `EmojiPickerFooter`; a Block Kit select's options (`c-select_options_list__option`); and a tooltip's `c-tooltip__tip`. A submenu's rows report the `Menu` they're in, as the root menu's do.

### Freezing the window

Some things show only while the pointer is on them: a message's hover toolbar, a tooltip, a hover card, a button's hover colour. Picking one usually means moving the pointer off it, and then it's gone. F holds the window on the frame on screen instead. Hover the thing, press F, and the window stays exactly as it was drawn, hover states, tooltips, the caret's blink and the animated emoji included. The banner turns to "Frozen: click or drag to blur, then copy · shift-click copies at once · ↑ ↓ parent · F or Esc unfreezes".

The pointer then moves over the frozen picture. The outline follows what the frozen frame has under the pointer, ↑ and ↓ work as before, and a click, a Shift+click or a drag captures from the frozen frame. To get a toolbar, freeze over its message, move off the message, then onto the toolbar where the frozen frame still draws it. In a live window the toolbar would be gone by then.

F again or Esc unfreezes, and the session goes on; Esc again ends it. Holding either key down counts once. A capture that ends the session ends the freeze too, and so does a new window size. While frozen the window lays nothing out, so nothing in it changes. A message that lands meanwhile reaches the client's data and shows when the freeze ends, and a report captured from the frozen frame describes that frame: its page, pane, overlays and theme are the ones from when the freeze began. Keys and clicks go to the tool alone, and the composer keeps the focus; nothing typed while frozen reaches it. On Windows an input method that is composing (Japanese or Chinese, say) keeps F to itself, so switch it to direct input first.

A session ends by itself when the sign-in screen comes up (the Slack session ended, Sign Out, another account) and when the window closes to the tray, frozen or not. Files dropped on the window during a session are ignored: nothing is attached or shared.

How it works. The tool keeps each session frame's ops as one call before it draws over them (Gio patch 31's `Ops.Whole`), and where they end in the window's ops (patch 3's `Ops.Checkpoint`). The tool reads a frame's input before the window resets its ops, so when F comes the frame on screen is still whole. From then on every frame rolls the window's ops back to that end and draws the tool's outline, label and banner after it, in place of a layout. They go in the window's own ops: Gio numbers the state a deferred drawing saves per `op.Ops`, so in ops of the tool's own a tooltip the window drew deferred (the reaction pill's) and the tool's drawing shared a number, and the frozen tooltip was drawn, and picked, at the tool's origin instead of its own (`TestFreezeDeferredTooltip`). What the tool appends after a rollback sits where the frame before's did, and Gio's GPU caches a path by its op's place in the ops: patch 3's `Rollback` starts a new epoch of op keys from the checkpoint on, so a path the tool draws in a frozen frame is never drawn as the one before it (`TestClackRollbackKeys`). The frozen frame's own inspect areas stay in the ops with their tags, so Gio's hit test still decides what the pointer is over, and slackc's `InspectFrame.Hold` keeps each area as its events left it. The image cache holds every animated image on the frame it showed (`imgcache.HoldLive`), the huddle window's too, which draws from the same cache. When the freeze ends, Gio patch 49 (`Source.ResetPointers`) catches every widget up before the window lays out again. No widget saw the pointer move while the window was frozen, so the reset sends what the router would have sent: a pointer Cancel to every widget, a Leave to each one that last heard the pointer come in and isn't under it now, and an Enter and a Move to each one under it. Every event carries the mouse's own pointer id, which matters on Windows, where the mouse is pointer 1 and a hover ignores another pointer's events. Without the Leave, the hovers that clear only on a Leave would stay: a message body's link and emoji tooltip, a plugin tree's :hover, a sidebar heading's ⋯ and +. The freeze holds one frame's ops, which stay in the window's own buffer, and lets them go when it ends. A window with no session pays nothing.

### Blurring before it's copied

After a click or a drag nothing is copied yet. The shot is shown still over the dimmed window, exactly as the copy will look, under the banner "Blur: drag over anything private · ⌫ undo · Enter copy · Esc cancel" (for a region, or a pick that found nothing, "Enter copy" joins it once Enter works, 300 ms after the review shows):

- drag rectangles over anything that shouldn't be shared (other people's messages, names, avatars). Each one is blurred out of the shot. Drag as many as you need, and the banner counts them.
- ⌫, Delete or Mod+Z takes the last rectangle back. A right click takes back the newest one under the pointer.
- Enter (or Mod+C) copies and saves the report with the rectangles baked into the image.
- Esc or Hyper+D drops the report: nothing is copied or saved.

A blurred rectangle holds nothing of what was under it. It is filled from the nearest pixels outside every rectangle (on each side, level with the pixel, the nearer side weighing more), then smoothed 6 dp. It is not a blur of its own pixels, so no deblurring or sharpening can bring a name or a face back. The rectangles are painted over the shot before the margin is blurred, so the margin's smear carries nothing of them either. `TestComposeRedactKeepsNothingInside` composes two shots that differ only under a rectangle and requires the two images to be identical. The report's text says how many rectangles the reporter blurred.

Then (at once for a Shift+click, on Enter for the review) Clack:

1. draws the report as a panel under the shot, on the CPU with the Go fonts. The image is as wide as the shot, or as the panel's 600 dp minimum for a small one (the shot sits centred above the panel at its own size),
2. copies that one image to the clipboard, so a paste in #clack carries both,
3. saves the image and the report's text as `inspect-reports/inspect-<date>-<time>.png` and `.txt` in the config folder, readable by the owner only.

Where the system can't copy images (Linux without wl-copy or xclip) the report's text goes on the clipboard instead, and the image is still saved. Where there is no shot at all (the headless capture failed) the report's text is copied at once, with no review.

### Drawing on it

The review has a pen too (Karim, 2026-11-21: "also add an drawing thing to the dev tools, optional tho"). P in the review turns it on, and the banner turns to "Draw: …". P in a session, frozen or not, grabs the whole window as a region (the report's capture row says `whole window`) and opens its review with the pen already on.

- Drag over the shot to draw a freehand line. Hold Shift at the press for a rectangle. A switches drags to arrows and back.
- 1, 2 and 3 pick red (the default), yellow and blue for the next line. Every line is 3 dp wide: 3 px at 1x, 6 at 2x, and as wide in the copy.
- Z, Mod+Z, ⌫ or Delete takes the last line back. Esc mid-line drops only that line.
- Esc or P goes back to blurring and keeps the lines. Esc again drops the review as before.
- Enter or Mod+C copies the image with the lines burned in, on top of the blur and the outline.

The lines are kept in the shot's pixels, as the blurred rectangles are. The review draws them over the shot with Gio, and the copy draws them on the CPU (`burnStrokes` in `internal/ui/inspect/draw.go`). The report doesn't change: its colours come from the shot as it was shot, and no row mentions the lines. With the tool off none of this is in the window: no key filter, no pointer area, no frame. `TestPenStrokesInCopy`, `TestPenUndo`, `TestPenEscBackToBlur` and `TestPenOffAddsNothing` pin all of this, and flake-check's `inspect-draw` job runs them.

## What the report says

| row | what |
|---|---|
| capture | `dragged region` for a drag, `whole window` for P's grab to draw on; absent for a click |
| component | the innermost Slack component boundary under the pointer (`slackc.Render`/`Component`), and whether a plugin patches it. A dragged region has none |
| element | its root element as a selector, Slack's classes and `data-qa` included; for a chrome element picked itself, that element |
| within | the enclosing components, innermost first |
| classes | the elements around it (`div.c-message_kit__message < …`) |
| tree, style | inside a plugin's host tree: the boxes under the pointer and the innermost one's computed colours and font |
| rect, pointer | in dp, window coordinates |
| region, page, overlays | the shell column (for a dragged region, every column it takes in), the redacted route, the popups open |
| blurred | how many rectangles the reporter blurred out of the image |
| ids, kinds | tags for the ids the components were drawn for, and what kind of conversation a tagged channel is |
| colors | the element's background and ink, and the pixel under the pointer, read from the screenshot |
| window | light or dark, the account theme, the UI font, size, scale and zoom |
| experiments | the experiments the element's code read while it drew, then the ones read around it |
| patches | the components plugins patch |

## Redaction

The report is meant for #clack, so it holds no content. It never collects message text, names, topics, emails, search queries or tokens. It is built from component names, classes, sizes, colours and tags.

An id becomes a tag: its kind and the first 6 hex digits of SHA-256 over a salt and the id (`ch:3fa2b1`, `user:77ab02`, `ts:9c01de`). Each report gets a new random salt, which is never written anywhere. Within one report the same channel always has the same tag, so "the same message" and "another one" stay apparent. Across reports, and for anyone without the salt, a tag says nothing. Routes keep their page (`c/`, `dms`) and tag every other segment. A run-time attribute value (a channel id in `data-qa-channel-sidebar-channel-id`) becomes a tag unless it is an enumeration such as `data-qa=add_reaction`.

clack.log uses the same tags for what a report about a navigation needs (`internal/ui/navlog.go`), with one salt per run that is never written. Within one log the same message keeps its tag, and nothing in a line names a conversation or a message. No text is logged. A line is written for:

- every thread pane that opens: `ui: thread opened: ch:… ts:… [at ts:…] [in the split view] (<source>)`. The source is what the entry point named (`a notification's click`, `a deep link`, `permalink from <caller>`, `message mention from <caller>`, `a message from <caller>` for a search result or Activity's Open in home, `its pane found the root was a reply`), else the first caller outside the router, as `ui/views.(*Activity).update activity.go:784`;
- every jumpToMessage, with the thread it resolved (`-` for none): `ui: jumpToMessage: ch:… ts:… thread ts:… [in the split view] (<source>)`, and when its lookup found no message: `ui: jumpToMessage: ts:…'s thread_ts wasn't found; navigating without it (<source>)`;
- a reply's ts that was turned into its thread (the guard for a slack://…thread_ts=<reply> link, docs/PARITY.md): `ui: jumpToMessage: its thread_ts ts:… is a reply in ts:…, whose thread opens at it (<source>)` or `ui: thread open: ts:… is a reply in ts:…, whose thread opens at it (<source>)`, or, when the pane only found out from conversations.replies, `ui: thread pane: its root ts:… is a reply in ts:…, whose thread opens at it [in the split view]`;
- every click on or reply to one of Clack's notifications: `notify: clicked a notification: ch:… ts:… thread ts:… (id type "msg")` (`replied to` for a reply, whose text isn't logged), and a button: `notify: a notification's button 1 (a link: false)`;
- every notification decision, for a message the socket brings and for the server's desktop_notification (a followed thread's reply): `notify: show ch:…/ts:…`, or `notify: skip <reason> ch:…/ts:…` with Slack's own number for the reason, as its maybeShowNotification logs them (6 a reply that doesn't mention you, 7 a desktop_notification that isn't a reply, 16 on screen in the focused window, 19 newer than every message the client took, 20 its thread read to it, 29 a hidden sender, …; `internal/ui/notify_decisions.go` lists them all), or a word for the checks Slack logs by text (`pref-disabled`) and the few Clack has alone (`ephemeral`, `deleted`). A notification that waits for a lookup writes its line once the lookup answers;
- a slack: link Clack doesn't handle, by its command only: `ui: deep link not handled: slack://<command>` (`a https link` for anything else).

The reads a navigation makes tag their ids the same way: `history ch:…: 120ms (network)`, `history ch:…: around ts:… in 80ms` (a jump's window), `history ch:…: older than ts:… in 60ms` and `history ch:…: newer than ts:… in 60ms` (its pages), `history ch:…: side <what> 40ms`, `tabs ch:…: 3 tabs (1 files) in 90ms`, and a failed lookup's `messages.list: 1 channels: <error> (ch:…)`.

The image shows the picked element as the user saw it, and of the rest of the window only the blurred margin around it, or a dragged region as it was. Whatever the element or region holds (a picked message's text) is in it, unless the user blurs it out in the review. A click (or a drag over it) opens the review before anything is copied or saved, so the user decides what to share; a Shift+click copies the element as it is, for when nothing in it is private.

## Coverage

Coverage is best inside Slack component boundaries: messages and their parts (sender, avatar, text, reactions, the reply bar, attachments), the sidebar's items, the composer, search, activity rows, menus and more, about 90 names in all. The chrome Clack draws without a component around it is marked for the tool alone with Slack's classes and `data-qa` (`slackc` `ClassDef.Inspect` and `InspectArea`: recorded for the picker, never on the element stack, so no selector matches them and nothing draws differently), as a browser's inspector reaches any element: the channel header (`.p-view_header`, its title button, the channel's name `span.p-view_header__channel_title`, the icon, the topic container, the actions), the tab bar (`c-tabs__tab_menu`, each `c-tabs__tab` and its title `c-tabs__tab_content`), the top nav (its containers, the history buttons, the search box and its text), the tab rail (`.p-tab_rail`, each `p-tab_rail__button` with Slack's `data-qa`, `tab_rail_activity_button`, its icon and label, the user button), and the Activity view's saved-view tabs and their titles. Plugin host trees go down to their boxes, through slackc's own hit test; of two trees under the pointer the one with its own element there wins, so an element a plugin puts among a native's children (UserPronouns' span in BaseBroadcastPreamble) is picked, not the native's box in the tree around it.

Closed since α.88:

- the Activity filter bar (Karim, α.85: the Unreads filter button couldn't be picked). The bar and its parts are marked with Slack's component names (`slackc.InspectAs`: a name for the picker only, which no plugin can patch; the names come from `docs/PLUGINS-props-live.md`): `ActivityFilterBar`, `ActivityFilterBulkAction` (the select group), `ActivityFilterUnreadsButton`, `ActivityFilterByMenu`, `ActivityFilterBySpecific` (the In pill), `ActivityFilterSearch` and `ActivityFilterLayoutToggle`.
- the message hover toolbar's buttons (`button.c-button-unstyled.c-icon_button… .c-message_actions__button` with their `data-qa`). They were entered with no box, so the picker landed on the whole `MessageActions` card.
- the top nav's bare parts on macOS, Linux and Windows, and the Windows caption buttons. Their system action areas took the press before the tool saw it, so a click there started moving the window (or minimized or closed it). A session now lays out none.
- popups (2026-11-18, above): modals, menus, popovers, the emoji picker, profile cards and tooltips. A menu's boundaries outlined the whole window, and nothing inside a Block Kit modal could be picked.
- inside profile cards and popovers (2026-11-19): the card was recorded after its content and picked over all of it, so a name, a presence dot or a peek's row outlined only the card. Also the Ctrl+K switcher's padding and footer and Block Kit's select dropdowns (they outlined the window column or the modal under them), plugins' overlay roots (they reported the window's region), and a plugin tree's tooltip in a light theme (the picker went through it).

Still not pickable as themselves, found by a static pass over the source (files with no component boundary or inspect mark inside them) rather than live. Each is reported as the nearest component around it, or as the shell column (sidebar, primary, secondary, top nav, tab rail) when nothing encloses it:

- the message list itself and the toolbar's quick-reaction emoji;
- the inside of channel details (`details.go`, `details_more.go`, `details_agents.go`, `details_posting.go`), Later, Drafts, Files and channel files, Unreads, Huddles and their history, folder tabs, the file picker and canvas comments;
- Preferences pages, the sign-in card and the introduction screens, the workflow pages and the drop overlay.

The drag is the way to capture any of these. Naming more of them means a boundary or an `InspectAs` mark with Slack's component name where Slack has one.

How it finds what is under the pointer: while a session records a frame, slackc puts a pass-through pointer area over every component it draws and every chrome element marked with a size, with a new tag each frame. Gio sends an Enter to each new area under the pointer, so Gio's own hit test (clips, and whatever is drawn over them) decides what counts. `internal/ui/slackc/inspect.go` has the details.
